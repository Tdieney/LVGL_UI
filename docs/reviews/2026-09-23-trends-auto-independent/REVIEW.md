## Findings

1. **P1 — Trends metric switch pushes a large dirty region.** Test-only [perf probe](perf_probe.c) uses the production UI plus the actual 800×10 RGB565 partial draw buffer and counts LVGL flush rectangles after 16 valid points/metric. Switching to another populated metric sends 151,615–160,984 pixels, 303,230–321,968 RGB565 bytes, in 25–27 flush calls. One hundred rapid switches send 31,313,358 bytes/2,623 calls; same-metric selection sends zero. The host CPU time in this probe (~31 ms/100 switches) is **not** MCU render time. The device QSPI speed, DMA completion, cache/memory bus and touch latency remain unmeasured. Source path: `ui_select_trend_metric` immediately updates both selectors and chart; `update_trends_page_widgets` changes chart count/range/points and several labels; custom draw shades every line segment with alpha polygons. `lv_chart_set_range` and `lv_chart_refresh` invalidate the chart; selector styles are removed/added on each change. This is credible bus/CPU pressure, not a proven exclusive cause of the owner's lag.
2. **P2 — a long telemetry gap makes the plotted time spacing false.** `ui.c:4020–4028` caps `diff` at 16 but fills gaps from the *old* minute. With the last sample at minute 0 and recovery at minute 100, retained slots are minute 1…15 and 100, while the chart spaces them evenly and the four axis ticks are interpolated across 1…100. The test-only probe reproduces `count=16 first=1 second=2 penultimate=15 last=100`. Fill only the final 16-minute window or otherwise ensure plotted timestamps match slot spacing; add long-gap regression.
3. **P2 — autonomous elapsed time wraps after 24 hours.** `ui.c:4014,4024,4027` stores `session_min % 1440`; `format_trend_time_label` and tooltip format that modulo value as elapsed uptime. At 24 hours the probe prints `elapsed_24h=+0m`. Preserve honest elapsed-session wording across days within constrained storage, or explicitly label a bounded recent-window-relative axis; do not present zero elapsed.
4. **P2 — equal-value external handoff keeps a stale axis.** `ui_feed_history` sets external ownership before the identical-data early return (`ui.c:3654–3679`), but does not increment the history revision. A matching one-point external feed should change the axis from relative `+10m` to wall-clock `00:10`; the probe shows `owner_before axis=+10m rev=4`, `owner_after axis=+10m rev=4 external=1`. Treat ownership/time semantics as a render change even if samples are byte-for-byte equal, without unnecessary redraw for a second identical external feed.

## Motor-control comparison and optimization direction

Read-only `git show ui/motor-control:ui.c` and `git show ui/motor-control:docs/PERFORMANCE_MEMORY.md` (no branch checkout). The old UI coalesces rapid tab taps into a single pending destination and renders selected navigation chrome before rebuilding the heavy content. It also profiles *pixels and flush calls*, not just frames. Transfer the **technique**, not motor UI screens or its fixed 90 ms throttle. Current Smart Hub already collects history off-page and already uses fixed buffers/one partial draw buffer; those are not gaps to reimplement.

Recommended order for a coding agent: (1) add reproducible switch/steady-state profiler around current 16-point/gap/empty data and target timing at touch, LVGL render, flush start/completion, bus bytes/calls; (2) minimize invalidated chart/selector area and redundant style/label/chart mutations while preserving exact accepted appearance; (3) if measured target latency remains visible, coalesce rapid metric requests and separate immediate selection feedback from deferred chart redraw in application context, with correct latest-tap semantics and no display-port reentrancy; (4) optimize alpha polygon rendering only if timing proves CPU bound. Compare before/after **pixels, calls, wall time, heap/transient peak, and screenshots**. Do not add a full framebuffer, second draw buffer, large cache, or new per-tick allocation to an MCU already near its RAM limit.
