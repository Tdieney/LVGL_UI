# Independent review — 2026-09-24 Trends delivery

Review-only. Examined the attached transcript, submitted [report](../2026-09-24-trends-final-delivery/REPORT.md), UI, tests, verifier, RAM baseline and artifacts. No production code, commit or push was changed. Reviewed source and both simulator hashes match the submission.

## Disposition

Both default and 40 KiB suites independently pass 40/40. History repair, burst request coalescing and some host flush savings are real. **The claimed feedback-first latency fix is not accepted:** the normal regression passes when Stage 1 flushes zero pixels, while the standalone benchmark forces an immediate refresh that the normal application loop does not. Target LCD latency remains unmeasured. [One CURRENT](../../prompts/CURRENT.md) covers remaining issues.

## Findings

1. **P1 — Stage-1 feedback is not proven visible and can collapse into Stage 2.** `ui.c:1418–1437` changes LVGL state but only invalidates objects. The simulator loop calls `ui_tick()` before `lv_timer_handler()` (`sim_pc/main.c:8207–8214`), and `ui_tick()` consumes the pending chart (`ui.c:4091–4095`). CHECK39 accepts `stage1_flushes == 0` and `stage1_pixels == 0` (`sim_pc/main.c:7074–7110`). Both independent 40/40 runs print `Stage 1: 0 flushes, 0 pixels; Stage 2: 24 flushes, 148381 pixels`. The standalone benchmark instead calls `lv_refr_now(NULL)` (`benchmark_fixture.c:54–59`) after directly injecting a click; it measures a different schedule with immediate-completion flush. Its Stage 1 is **42,080 px/6 calls**, exceeding CHECK39's nominal 35,000-px budget. Its coarse `clock()` 0.00 ms cannot establish `<5 ms` or touch-to-photon latency. No delayed asynchronous flush test is present.
2. **P1 — interim title can misdescribe the old plot.** `on_metric_tab_click` changes `s_selected_metric`, then `update_trends_tabs()` updates the chart title (`ui.c:1395–1415`) before deferred chart/stats/axis update. If Stage 1 is visible while Stage 2 waits, the old chart appears under the new title. CHECK39 checks only the final unit, not intermediate consistency. Pending-switch telemetry, tooltip and page-exit interactions are also not covered by the new staging tests.
3. **P2 — Windows verifier's fail-closed claim is incomplete; this is not MCU code.** `Get-VerifiedProcessTree` throws on CIM enumeration error (`tools/verify_production.ps1:52–57`), but worker polling loops discard the exception (`:263–276`, `:335–346`), allowing a phase to continue after losing descendant visibility. Fixture 6 (`:568–582`) checks only an exited process, not denied enumeration or kill. `Terminate-OwnedProcessTree` also accepts raw `RootPid` with no expected creation time (`:116–136`), though current production call sites pass one. Restrict that path and prove failure propagation using controlled owned processes/mocks.
4. **P2 — E2 coverage/report overstates CHECK40.** The new `sim_pc/main.c:7167–7400` sequence is procedural, not table-driven. It checks Home, one Temperature Current label and a Fan fault editor; later Purifier valid zero and Fan actuation. It does not assert all four Trends metrics' Current/Min/Max/chart-gap retention across combined fault and partial recovery or all three Auto editors. CO2 gap is asserted, but VOC gap and unaffected Temp/Humidity histories are not. Keep accepted Auto behavior and extend only missing assertions.
5. **P2 — RAM/visual evidence needs reconciliation.** The host allocation wrapper and contemporaneous block samples are useful; 40 KiB transient free reaches **1,896 B**, so target approval still requires full firmware map/stacks/DMA/radio. `docs/MCU_BASELINE.md` says draw buffer 16,000 B; the report later says 25,600 B. Baseline 40 KiB settled/free/drift values differ from the new log (6,248 B minimum, +0 B drift). Captures exist, but there is no same-state before/after pixel comparison. Correct the reporting; no appearance redesign is warranted.
